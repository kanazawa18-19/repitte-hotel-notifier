# state（last_processed.txt）の設計と、そう決めた理由

このファイルは 2026-09-26 に `AGENTS.md` から中身をそのまま移したもの（2026-09-10 時点の設計経緯）。触る前に読む場面は `AGENTS.md` の表にある。再測定した数値は末尾の「実測値」表だけ直す。

## state（last_processed.txt）の扱い

**読み始める起点は、最初の1回だけ決めて保存する**（`monitor.ensure_last_ts`）。

```
   ✗ 旧実装                          ○ 現在
   ─────────────────────────────     ─────────────────────────────
   新着0件の回は state を書かずに     起点を1度だけ決めて保存する。
   そのまま return                    空振りの回は据え置く

   → state を失うと二度と作られず     → 実行が何時間空いても
     毎回「今から30分前」が起点に        「前回の続きから今まで」を必ず読む
```

- **state に入れてよいのは「Slackが発行したts」と「初回に決めた起点」だけ。**
  こちらの時計から作った値を毎回書き足す設計に戻さない
  （ランナーの時計がSlackより進んでいると、まだ届いていない時刻まで読んだことになる）
- **起点の保存は取得の前に行う。** 取得が失敗した回でも起点が残る
- `conversations.history` は**必ずページングする**（`fetch_all_messages`）。
  1ページ目だけだと、取得窓に51件以上あるとき古い方が二度と読まれない。
- **★ 全部取れたと言い切れないなら、1件も処理しない。**
  `MAX_PAGES` 超過も、`has_more=true` なのに次のカーソルが無い異常応答も、
  **黙って「取れた分」を返さず例外にする**。Slackは新しい順に返すので、
  部分取得を全部だと思って state を進めると、**落ちるのは必ず古い方＝
  まだ転記していない契約報告**になる。その回を丸ごと失敗させる方が安全

### ★ 記録するのは「窓の端」ではなく「処理し終えた最後のts」

```
   投稿A ── 転記成功 ──▶ ここまで進める
   投稿B ── 転記失敗 ──▶ 打ち切る。次回はBから 読み直す
   投稿C ── まだ見ていない
            ▲
            │ 窓の端（C）まで進めると、Bが誰にも転記されないまま埋もれる
            │ 一切進めないと、Aが次回また投稿されて #repitte-hotel に二重に並ぶ
```

| 失敗した場所 | state | 理由 |
|---|---|---|
| 本体の転記（`post_contract`） | **進めない**。そこで打ち切る | まだ何も投稿していないので、やり直しても二重にならない |
| 添付・リマインド（`post_extras`） | **進める**。スレッドに警告を残す | 本体は投稿済み。進めないと本体が二重に並ぶ（重複より欠落を選ぶ） |

**★ 「1件ずつ進める」は、その場でファイルに書くという意味。**
ループの外でまとめて1回書く作りに戻さない。例外は拾えても、
ジョブのタイムアウト・SIGKILL・ランナー障害は拾えない。書き込みに到達しないまま死ぬと、
投稿済みの契約報告を次回また投稿する。**投稿した直後に書く。**

**★ 添付の失敗は必ず例外にする**（`upload_file`）。
ログを1行出して戻る作りに戻すと、「失敗したらスレッドに警告」の経路をすり抜け、
**契約書の添付が付かないまま誰にも気づかれず終わる。**

- `advance_last_ts` は**前より古い値では上書きしない**。巻き戻ると、そこから全部読み直して
  転記済みの契約報告を丸ごと再投稿する
- ワークフローに `concurrency` を入れてある。**外さない。**
  stateを読んでから書くまでに別のrunが割り込むと、両方が同じメッセージを転記する

### ★ 未来の ts が state に入ったら、引き直して人に知らせる

**2026-09-10 に [[cnctor-onboarding]] の `7a5d737` から移植。**

```
   state に未来の ts が入る
        │  そのまま conversations.history の oldest に渡る
        ▼
   「それより後の投稿」は当分存在しない → Slackは毎回0件を返す
        │  例外は出ない。Actions は緑。ログは [EMPTY] が並ぶだけ
        ▼
   #job_sales が静かなだけの回と、ログ上まったく見分けがつかない
        │  しかも advance_last_ts が巻き戻しを禁じている
        ▼
   契約報告が届いても永久に転記されない。自力では戻らない
```

`_read_state_raw()` が3つを見る。ここを緩めない。

| 見るもの | 弾く値の例 | 理由 |
|---|---|---|
| 数値として読めるか | `"こわれています"` | `invalid_ts_oldest` で毎回失敗し続ける |
| 有限かつ正か | `-1` / `-inf` / `nan` / `0` | 「float になる」だけでは通しすぎる |
| **現在時刻＋60秒より先でないか** | `5000000.0`（ミリ秒のepoch等） | 上の図の永久停止 |
| **古すぎないか（90日）** | `1` / `100` / `123456` | 別の形の永久停止（下記） |

**★ 未来だけ見ても足りない**（2026-09-10 の GPT-5.6 Sol 指摘）。

```
   state に 1 が入る（有限で正なので、未来の検査は素通りする）
        ▼
   oldest=1 → #job_sales の一番古い履歴からページングが始まる
        ▼
   MAX_PAGES に到達して例外 → stateは 1 のまま（進めないので直らない）
        ▼
   次回も、その次も、同じところで落ち続ける
```

未来のときと違って実行は**赤くなる**が、止まっていることに変わりはない。
`MAX_CATCHUP_SEC = 90日` の根拠はコード側のコメントにある（ページング容量から逆算）。

**★ 未来の ts を「記録した」ことも、その回のうちに知らせる**（同・GPT-5.6 Sol 指摘）。

```
   ✗ 未来だから保存しない   → 次回その契約報告をもう一度転記する（二重転記）
   ○ 保存はする ＋ 保存した事実をこの回のうちに検知して赤くする
```

`advance_last_ts` は未来のtsでも記録し、`True` を返す。`main()` は転記を最後まで
済ませたうえで実行を赤くする。これが無いと、異常値を書いた回は緑で終わり、
次の実行（GASの起動係で30分後）まで誰も気づけない。

- **`FUTURE_TS_TOLERANCE_SEC = 60` を広げない。** この幅がそのまま「見逃す時間」になる
  （許容した未来の値は引き直されないので、現在時刻が追いつくまで0件が返り、
  その間に届いた投稿は「起点より古い」ので二度と取れない）。
  値そのものは `tests/test_state.py::test_許容幅は60秒から広げない` で固定してある
- **直すのは即座に。伝わるのを待たない。** 引き直す先は「そのとき」から30分前なので、
  直すのを遅らせた分だけ欠落がまるごと広がる
- 伝えられなかったお知らせは `pending_repair_notice.json` に残し、**伝わるまで毎回言い直す**。
  直した次の回からは正常な state に見えるので、残さないと二度と言い直せない
- **お知らせが出せないことを理由に監視を止めない。** 赤くするのは全部やり切った後
  （`main()` の末尾）。止めると、伝えたかった取りこぼしがその間さらに増える
- **`write_last_ts` / `write_repair_notice` は atomic に書く。** 途中で落ちたときに
  0バイトの state が残ると、突然死しただけでリピッテチームへ重い確認依頼が飛ぶ

**★ 読み取り側と書き込み側の非対称は意図的。** `advance_last_ts`（書き込み）は
未来かどうかを見ない。ここに来るのは「いま転記し終えたメッセージのts」なので、
未来に見えるからと記録を拒むと、**次回その契約報告をもう一度転記する**。
記録側は実際に処理したところを正直に残し、直すのは読み取り側の仕事にする。

**★ 残っているリスク（2026-09-10 の shirokuma-sec 指摘。承知のうえで残した）**

引き直し先は `now - 30分` なので、**正常な state を誤って「壊れている」と判定すると、
直近30分ぶんを読み直して二重転記になる。** 発火には
「ランナーの時計が Slack より60秒以上遅れる」ことが要る（NTP同期されているので
実質起きない。ただし**未実測**）。区別する術がこちらに無いので、
お知らせの文面で**取りこぼしと二重の両方**を確認してもらう形にしてある。

**★ 長く止まったあとに壊れが見つかると、30分より前は取り返せない**
（2026-09-10 の Gemini Pro 指摘。承知のうえで残した）。

```
   トークン失効などで bot が1日止まる
        ▼
   復旧させた初回に state が壊れていると判定される
        ▼
   引き直し先は now-30分 → その1日ぶんは、どの取得範囲にも入らない
```

`INITIAL_LOOKBACK_SEC` を広げれば拾えるが、**広げてはいけない**（下の節を参照）。
広げると、stateを失った回に古い契約報告をまとめて転記してしまう。
この場合の回収は `scripts/probe_flow.py`（読み取り専用・手動実行）で事後に数える運用。
**通知文で「本日の投稿と見比べてください」と頼んでいるのはこのため。**

**★ 許容幅を 15〜30 秒へ縮める案は見送った**（2026-09-10 の Gemini Pro 提案）。
「NTPのずれは数秒〜十数秒なので、60秒は広すぎる」という指摘自体は正しい。
それでも60のままにしたのは、[[cnctor-onboarding]] が同じ値を使っているため。
契約報告は90日で5件しか流れないので、見逃す幅が60秒か30秒かで拾える件数は変わらない。
**2リポジトリで値が違う方が、後から読む人を迷わせる。**

**★ 「一度きりの事故」ではない。** 時計の遅れが続いている間は、毎回この形になる。

```
   1回目  正しく転記 → advance_last_ts が書き込む（Slackのts＝ランナーから見て未来）
   2回目  read側が「未来」と誤判定 → 30分巻き戻し → 同じ投稿をもう一度転記
   3回目  同じことが起きる
          ▲ 原因（時計の遅れ）が直るまで、二重投稿が毎回続く
```

原因がランナー側に持続していると**永続的な二重投稿ループ**になる
（2026-09-10 の shirokuma-sec 2周目指摘）。#repitte-hotel に同じ報告が
繰り返し並ぶのを見たら、まずこれを疑う。確かめ方は Actions のログで
`[REPAIR] ★stateが壊れていた` が毎回出ているかどうか。

### state の永続化は `monitor.yml` とセット

`monitor.py` が `write_last_ts()` でファイルに書いても、それだけでは次回の実行に残らない。
**`monitor.yml` の `Save state` ステップが commit / push して初めて記録になる。**
`if: always()` が付いているのは、監視本体が落ちた回でも起点だけは残すため。
**片方だけ直さない。** state の扱いを変えるときは必ず両方を見る。

**★ `pending_repair_notice.json` を `git add` する分岐は pytest の対象外。**
`monitor.yml` のシェル分岐（`[ -f ... ] || git ls-files --error-unmatch ...`）は
テストで守られていない。2026-09-10 に使い捨ての git リポジトリで
「未追跡で存在しない／新規に出来た／追跡済みが削除された」の3ケースを手で通し、
いずれも意図どおり（何もしない／`A`／`D`）であることを確認した。**ここを触ったら同じ3ケースを手で通すこと。**

**★ `git pull --rebase` を外さない。** botの実行中（1〜2分）に誰かが main へ push すると、
`git push` が non-fast-forward で失敗する。**失敗すると state が保存されず、
次回また同じ起点から読み直して転記済みの契約報告を二重に投稿する。**
[[notes-sync]] が毎時同じ理由で失敗していたのと同じ形。

### まだ塞いでいない穴（at-least-once）

`chat.postMessage` が Slack に届いて**返事が返る前**に通信が切れると、
こちらからは失敗に見えるが Slack には投稿が存在する。次回やり直すと二重に並ぶ。
state だけでは原理的に塞げない。塞ぐには元投稿の `channel + ts` を一意キーにした
転記済み記録（[[cnctor-onboarding]] の `processed_contracts.json` 相当）が要る。

**★ 塞ぐなら、破損時の巻き戻し幅の問題と一緒に解ける**
（2026-09-10 に Gemini Pro と GPT-5.6 Sol が独立に同じ形を提案）。

```
   転記先のメッセージに、元投稿の source_ts を機械的な一意キーとして残す
        ▼
   転記を source_ts 単位で冪等にする（既に転記済みなら skip）
        ▼
   state が壊れたときは 30分ではなく 90日など十分大きく巻き戻せる
        ▼
   既転記は skip され、未転記だけが回収される
```

いまは「二重転記が怖いから30分しか戻せない」という縛りがあり、
そのせいで長い破損期間ぶんを取り返せない。冪等にすればこの縛り自体が消える。
**流量が90日で5件なのでDBは要らない**（転記先の投稿を読み直して照合すれば足りる）。
**現状は at-least-once。** 実測の流量（1日約8件・契約報告は90日で5件）では
起きる確率が低いので、今は入れていない。

### 実測値（★ここが正本。コードやテストに数値を書き足さない）

| 測ったもの | 値 | いつ |
|---|---|---|
| 実行間隔（cron は `'*/5'`） | **中央値433分／最大2925分／24回中24回が60分超** | 2026-09-10 |
| 1回の取得窓が50件を超えた回数 | 0個（#job_sales は1日約8件） | 2026-09-10（直近90日） |
| リピッテホテルの契約報告 | 直近90日で5件（最後は 07-31） | 2026-09-10 |

再測定したらこの表だけ直す。同じ数値を `monitor.py` や `tests/` に書くと、片方だけ古くなる。

**`INITIAL_LOOKBACK_SEC = 1800`（30分）を広げない。**
実行間隔の実測（中央値433分）より遥かに狭いが、この値が使われるのは
**stateを失った直後の1回だけ**で、実行間隔とは無関係。広げると、その1回で古い契約報告を
まとめて転記してしまう。stateが壊れた回の取りこぼしは `scripts/probe_flow.py`
（読み取り専用・手動実行）で事後に数えて拾う運用。

同じ形の不具合と直し方は [[cnctor-onboarding]] の `core.ensure_last_ts` にある。
